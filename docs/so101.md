# SO-101 simulation

The SO-101 follower has five arm joints and an independent gripper. The `so101`
benchmark runs the official manufacturer model in a Robosuite/MuJoCo world,
using the shared CaP API and recorded-run format. Its initial task is a fixed
control scene, not a manipulation or generalization benchmark.

## Install and run

Use the Linux Robosuite environment described in [host setup](host-setup.md):

```bash
bash scripts/bootstrap_robosuite.sh
source .venv-robosuite/bin/activate
bash scripts/bootstrap_so101.sh

python -m cap_harness.cli run \
  --benchmark so101 --suite so101_control --task-id 0 --seed 1 \
  --program examples/robosuite/so101_aspire_control.py \
  --output-root outputs/so101-control --max-steps 300 \
  --camera-width 320 --camera-height 240
```

Choose the MuJoCo rendering backend appropriate to the host as described in
[Robosuite setup](robosuite.md). No perception or planning model service is needed
for this task. The backend exposes joint control and built-in joint interpolation;
Cartesian IK and collision-aware planning providers are not configured.

The example moves and returns all five joints, then closes and reopens the jaw.
The host evaluator requires every joint to move by at least 0.12 rad and return
within 0.01 rad of its initial angle. It also requires the close/open sequence
after those returns, with normalized jaw thresholds of 0.03 and 0.97, and the
arm at home on completion. Moving only one joint does not complete the task.
The evaluator's state and success predicates stay outside generated-program tools.

Every run records source, actions, observations, outcomes, and the two videos
`media/videos/agentview.mp4` and `media/videos/sideview.mp4`. Inspect `outcome.json`
for both `program_ok` and `task_success`, rather than treating process exit as
task completion. See [recorded runs](run-artifacts.md).

## Official model and installation paths

The model comes from [TheRobotStudio/SO-ARM100](https://github.com/TheRobotStudio/SO-ARM100),
revision `a758567c3978dfeefe282ede0500085a48fe8f78`, using
`Simulation/SO101/so101_new_calib.xml`. The packaged manifest is
`cap_harness/configs/robots/so101.json`.

The bootstrap obtains the pinned model in `third_party/so_arm100`, keeps its
Apache-2.0 license, and rejects an unexpected origin or a dirty existing checkout.
The loader checks the revision and tracked changes again before use. The assets
remain separate from the framework wheel and Git commits. MuJoCo spec attachment
preserves the manufacturer's nested defaults, meshes, masses, joint properties,
actuator parameters, and contact parameters. The framework adds a work plane,
lighting, and cameras. Exported scenes resolve meshes against the installed model
tree and can be reopened from a different output directory on that machine.

For an installed wheel, or a model stored outside the source checkout, set:

```bash
export CAP_HARNESS_SO101_MODEL_ROOT=/absolute/path/to/so_arm100
```

This is the root of the pinned manufacturer Git checkout. The manifest ships
inside the package, so loading it does not depend on the working directory or
on an editable install.

## Control and camera conventions

The adapter exposes `primary` in `so101_base` and two fixed RGB-D views,
`agentview` and `sideview`. `so101.get_controller_metadata()` reports the model
commit, actuator bounds, angular jaw mapping, rate limits, and camera parameters.
`so101.get_task_metadata()` reports the task instruction and identity.
When projecting a depth mask with the shared `mask_to_point_cloud` helper,
request `target_frame="so101_base"` explicitly.

Servo target increments are capped at 1 rad/s for the arm and 3 rad/s for the
jaw, independently of control frequency. The control period must be an integral
multiple of the model's physics timestep. Invalid actions leave accepted goals
unchanged, and terminal episodes reject additional simulation steps.

RGB and depth use the same single-sample renderer. Pixel centers have principal
point `((width-1)/2, (height-1)/2)` and the metric depth clipping range is 0.02–5 m.
Analytic-plane tests check projection at two resolutions and camera poses, with a
tolerance of 1% of a pixel's physical footprint. A deliberate half-pixel error
must fail that criterion, guarding against a permissive numerical tolerance.

Direct joint commands and interpolation do not provide collision avoidance.
This backend supplies no physical-robot connection, force sensing, grasping,
perception service, or harvest-task implementation.

## Joint dimensions

Use `embodiment="so101"` when constructing SO-101 `RobotState`, `ArmCommand`,
`Trajectory`, and `RobotPlanningContext` values. The arm target contains five
angles in radians. The gripper remains a separate normalized value; adding it to
the arm vector would give the wrong contract shape.

Existing embodiments retain their declared joint counts: YAM has six, and the
Panda and R1 profiles have seven per arm. Omitting `embodiment` still selects
`robosuite`. Supplying an SO-101 vector with that default is rejected.

`CapApi(..., home_joint_positions=...)` now requires a finite vector with the
declared robot's joint count, for each supplied arm. Previously, any six- or
seven-element vector was accepted, even for a robot of the other dimension;
five-element homes were always rejected. Invalid configurations now fail during
API construction. Existing callers must provide a home matching their adapter's
declared embodiment.

## Absolute-position action encoding

`cap_harness.so101.codec.SO101ActionCodec` is a host-side building block for an
adapter. It converts one `primary` arm command into six actuator targets:

1. The five commanded arm angles, checked against supplied actuator bounds.
2. The gripper angle interpolated between its supplied bounds, with `0` closed
   and `1` open.

An explicit gripper command overrides the cached target. If omitted, the cached
target takes precedence over the measured opening, so a jaw stalled on an object
keeps its intended target through the next arm command. Without a cached target,
the measured opening is used. The codec rejects other embodiments, other arm
names, malformed actuator bounds, out-of-range arm targets, and invalid normalized
gripper targets. It encodes targets without sending them to any controller.

Actuator limits must come from the selected robot model or calibration. This
normalized interpolation is a simulation convention, not a calibrated conversion
to the physical LeRobot motor interface.

## Validation

The new tests exercise the contract boundaries and a fake adapter through
`set_gripper`, `move_to_joints`, and `go_home` for five-, six-, and seven-joint
robots. They verify that motion preserves the commanded gripper target and that
an explicit home is copied rather than aliased to the caller's array. Codec tests
cover gripper endpoints, intermediate openings, cached targets, and invalid
inputs. All of these checks run with the base and development dependencies.

```bash
python -m pytest tests/test_so101_contracts.py tests/test_contracts.py tests/test_api.py -q
```

With MuJoCo, Robosuite, the pinned model, and a working renderer installed, run:

```bash
python -m pytest tests/test_so101_adapter.py tests/test_so101_model.py tests/test_so101_camera_calibration.py -q
```

These integration tests check manufacturer-model fidelity, scene export, measured
motion, gripper continuity, stale trajectories, terminal handling, control-rate
invariance, RGB-D geometry, and a recorded run without model-service clients.
They skip explicitly when simulator dependencies or the model are unavailable.
No harvest or physical-robot success is implied by these checks.
